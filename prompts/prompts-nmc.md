Escenario 2 — Drag-and-drop de candidato entre fases

Nombre del test: 'should move candidate to another column and call PUT /candidates/:id with correct body'

Importante sobre drag-and-drop con react-beautiful-dnd:
react-beautiful-dnd no responde a los eventos nativos de mouse drag del navegador de la
misma forma en Playwright. Usa la siguiente estrategia robusta basada en teclado
(que react-beautiful-dnd sí soporta natively):

// 1. Foco en la tarjeta
const card = page.getByTestId('candidate-card-101');
await card.focus();

// 2. Activar modo drag con Space
await card.press('Space');

// 3. Mover a la siguiente columna con ArrowRight (una vez por cada columna)
await card.press('ArrowRight');

// 4. Soltar con Space
await card.press('Space');

Alternativamente, si prefieres simulación de mouse para mayor cobertura visual, usa
page.dragAndDrop() o la API page.mouse con las coordenadas del source y target.
Implementa ambas variantes como helpers y úsa la de teclado como principal.

Setup: Igual que Escenario 1 + interceptar también el PUT.

Intercepción del PUT:
Usa page.route('**/candidates/101', ...) para interceptar. Captura el request body
antes de responder:

let capturedBody: { applicationId: number; currentInterviewStep: number } | null = null;

await page.route('**/candidates/101', async (route) => {
  const request = route.request();
  capturedBody = JSON.parse(request.postData() ?? '{}');
  await route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify({
      message: 'Candidate updated successfully',
      data: {
        id: 201,
        positionId: 1,
        candidateId: 101,
        currentInterviewStep: 2,
        applicationDate: '2024-01-15T10:00:00Z',
        notes: null
      }
    })
  });
});

Assertions tras el drag:
1. La tarjeta candidate-card-101 ahora está visible dentro de phase-column-technical-interview
2. La tarjeta candidate-card-101 ya NO está dentro de phase-column-cv-review
3. capturedBody no es null (el PUT se disparó)
4. capturedBody.applicationId === 201 
5. capturedBody.currentInterviewStep === 2 (el id numérico de "Technical Interview")

Restricciones y consideraciones

1. Sin datos hardcodeados frágiles: todos los datos de prueba deben definirse como
constantes al inicio del archivo de test para facilitar su actualización.
2. Waitfor network idle: tras navegar a la URL, espera a que ambas peticiones mock
se resuelvan antes de hacer assertions:
await page.waitForLoadState('networkidle');
3. El positionId en la URL: usa 1 como ID fijo en los tests. Toda la red está
mockeada, así que el backend real no necesita estar corriendo.
4. Orden de page.route(): registra los mocks ANTES de llamar a page.goto().
5. No uses page.waitForTimeout(): usa waitForResponse, waitForLoadState,
o assertions con toBeVisible() que tienen retry automático.
6. Estructura del archivo: usa test.describe('Position Details Page', () => { ... })
como bloque contenedor. Extrae los datos mock a constantes fuera del describe.
7. Nomenclatura de data-testid: el nombre del data-testid de la columna debe
derivarse dinámicamente del nombre de la fase: lowercase + replace spaces con guiones.
Ejemplo: "CV Review" → phase-column-cv-review, "HR Interview" → phase-column-hr-interview.

import { test, expect, Page } from '@playwright/test';

const POSITION_ID = 1;
const BASE_URL = `http://localhost:3000/positions/${POSITION_ID}`;
const BACKEND_BASE = 'http://localhost:3010';

const MOCK_INTERVIEW_FLOW = {
  interviewFlow: {  
    positionName: 'Senior Backend Engineer',
    interviewFlow: {
      interviewSteps: [
        { id: 1, name: 'CV Review' },
        { id: 2, name: 'Technical Interview' },

const MOCK_CANDIDATES = [
  {
    candidateId: 101,

    currentInterviewStep: 'CV Review',
    averageScore: 3,

  },
  {
    candidateId: 102,

    currentInterviewStep: 'Technical Interview',
    averageScore: 4,
    applicationId: 202,
  },
];

async function mockInterviewFlow(page: Page) {
  await page.route(`${BACKEND_BASE}/positions/${POSITION_ID}/interviewFlow`, (route) =>
    route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify(MOCK_INTERVIEW_FLOW),
    })

}

async function mockCandidates(page: Page) {
  await page.route(`${BACKEND_BASE}/positions/${POSITION_ID}/candidates`, (route) =>

      status: 200,

test.describe('Position Details Page', () => {
  test('should display position title, stage columns and candidates in correct column', async ({

---
Problemas concretos que debes resolver

Problema 1 — Setup duplicado en cada test

mockInterviewFlow(page), mockCandidates(page), page.goto(BASE_URL) y
page.waitForLoadState('networkidle') aparecen copiados en ambos tests. Con más
tests, este boilerplate crece linealmente.

Solución esperada: mueve ese setup común a un test.beforeEach dentro del
test.describe. El fixture page está disponible directamente en beforeEach({ page }).

Problema 2 — Helpers acoplados al parámetro page

mockInterviewFlow y mockCandidates son funciones sueltas que reciben page
como argumento porque viven fuera del describe. Esto hace que sean difíciles de
descubrir y que su relación con el bloque de tests no sea obvia.

Solución esperada: convierte los helpers en funciones internas al describe,
o mejor aún, llámalas directamente desde beforeEach sin necesidad de que sean
funciones nombradas separadas — si el cuerpo es pequeño, inlínealas.

Problema 3 — BASE_URL construye la URL completa ignorando baseURL del config

El playwright.config.ts ya define baseURL: 'http://localhost:3000'. Usar
http://localhost:3000/positions/1 hardcodeado duplica esa información y hace
que un cambio de puerto requiera editar dos archivos.

Solución esperada: usa rutas relativas en page.goto:
await page.goto(/positions/${POSITION_ID}). Elimina la constante BASE_URL.

Problema 4 — BACKEND_BASE hardcodeado como string repetido

La URL del backend se repite en cada page.route(...). Si cambia el puerto,
hay que buscar y reemplazar manualmente.

Solución esperada: mantén BACKEND_BASE como constante (ya existe), pero
asegúrate de que todos los page.route la usen con glob patterns de Playwright
(**/candidates/101) para mayor robustez ante cambios de host. Aplica el mismo
patrón glob a las rutas de interviewFlow y candidates.

Problema 5 — capturedBody declarado con let fuera del scope donde se usa

En el test de drag-and-drop, capturedBody se declara como let ... = null y
luego se asigna dentro de un callback asíncrono. Esto es frágil: si el route
nunca se llama, el error de null aparece tarde y sin contexto claro.

Solución esperada: en lugar de capturar el body en una variable let, usa
page.waitForRequest (que devuelve una Promise) junto con Promise.all para
ejecutar el drag y esperar el request simultáneamente. Luego parsea el body del
request capturado. Esto elimina la variable mutable y hace el flujo lineal:

const [request] = await Promise.all([
  page.waitForRequest((req) =>
    req.url().includes('/candidates/101') && req.method() === 'PUT'
  ),
  performDrag(page),  // función que ejecuta el drag por teclado
]);
const body = JSON.parse(request.postData() ?? '{}');

Problema 6 — La secuencia de drag-and-drop no está encapsulada

Las tres líneas de teclado (focus, Space, ArrowRight, Space) están
inlineadas en el test sin ningún nombre que explique qué hacen.

Solución esperada: extrae una función async function dragCandidateRight(page,  candidateTestId) dentro del describe (o como helper local) que encapsule el
foco, el Space de inicio, el ArrowRight y el Space de drop. Así el test lee:
await dragCandidateRight(page, 'candidate-card-101');

Problema 7 — Locators inline repetidos

El patrón page.getByTestId('phase-column-X').getByTestId('candidate-card-Y')
aparece cuatro veces. Si el data-testid cambia, hay cuatro sitios que editar.

Solución esperada: crea un helper de locator (no async, devuelve un Locator):
function candidateInColumn(page: Page, columnId: string, cardId: string) {
  return page.getByTestId(columnId).getByTestId(cardId);
}
Úsalo en todas las assertions que combinen columna + tarjeta.
